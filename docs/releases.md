# Release process

HyperMug has two public channels. **Stable** is an owner-started workflow with an explicit `X.Y.Z` version and `vX.Y.Z` tag. **Canary** builds automatically when app or branding files change on protected `main`; each published run gets its own `v0.0.0-canary.N` tag and prerelease. A docs, website, skill, or cask-only change does not trigger Canary. Both channels test the exact source commit in GitHub Actions before first tagging; binary releases build from that same SHA.

## Stable: manual app or source

The owner starts **Stable** from `main`, enters `X.Y.Z`, and chooses **Build app** (default on). The `production` environment requires its owner review and permits runs from `main`. The workflow validates the owner actor and triggering actor, the source SHA, version ordering, and the immutable tag. A retry of a pre-migration tag tests and builds the exact selected old source checkout, while separately checked-out current main supplies trusted release and publishing automation. Source-only retries use the same trusted publisher without a binary build. It runs release metadata tests, Core coverage, compile, issue automation, and website checks before publication.

With **Build app** on, the macOS runner signs with Developer ID, notarizes and staples the app, verifies the ZIP and Sparkle signature, and publishes the ZIP, checksum, Stable appcast, and cask metadata in a GitHub Release. It advances only `appcast-stable.xml` and prepares the in-repo `Casks/hypermug.rb` metadata branch. Required CI and the trusted cask publisher then update the default branch automatically, without a release PR. A compiled Stable release is the GitHub latest release.

With **Build app** off, the same approved SHA gets an immutable tag and a source-only GitHub Release with GitHub's source archive. It has no app, binary checksum, signing/notarization claim, appcast entry, or cask update, and it is not marked as the latest installable release. Build the source locally with [Development](development.md). The most recent source version may therefore be newer than the most recent downloadable Stable app. Use the Stable feed or published cask to identify the latest installable Stable version; do not assume `/releases/latest/download/<asset>` exists for a source-only version.

Choose the mode before publishing. A published source-only release cannot gain assets while GitHub immutable releases are enabled; ship a later binary under a **new version and tag**. Do not move tags or replace published assets. A completed source-only retry is a read-only no-op; a compiled retry reuses its immutable published assets. Older versions cannot advance the Stable feed or cask.

## Canary: automatic binary

**Canary** runs on app-related protected `main` pushes. The existing internal `beta` environment holds its separate Canary signing and Sparkle keys and permits only `main`; the public product name and feed are Canary. The runner tests the exact push SHA, creates or verifies an immutable annotated tag, then builds, signs, notarizes, and publishes a prerelease. Its increasing workflow run number `N` identifies tag `v0.0.0-canary.N`, becomes numeric `CFBundleVersion=N`, and maps to Apple-compatible `CFBundleShortVersionString=0.0.N`. The Canary cask and appcast display `0.0.N`; the appcast still records the source tag and points to its exact release asset. Release and feed checks reject a queued run once a newer Canary release exists, so an older run cannot move `appcast-canary.xml` or the `hypermug@canary` cask backward. Canary never advances Stable's feed, cask, or GitHub latest release.

The Canary app embeds its own feed URL and public update key. A Canary installation follows Canary; Stable follows Stable. Both use the same bundle ID and settings, so [switch channels](installation.md#homebrew) by uninstalling the existing cask and installing the other. Only Stable and Canary are public channels. The obsolete Nightly cask is removed; historical beta releases remain immutable and existing users migrate manually. Canary binaries and the canonical cask are published automatically.

## Destinations and controls

Published assets and appcast files live in this repository. The release-bot App token is scoped to exactly this repository, so `RELEASES_REPOSITORY` must equal `SOURCE_REPOSITORY`. Each binary release prepares a cask commit on an internal `release-casks/<channel>` branch and its authenticated App push starts required CI. No extra CI dispatch is sent: duplicate push/dispatch runs can cancel a required check. A trusted-main `workflow_run` job accepts only a successful same-repository CI run on that exact commit, checks that the diff changes one regular cask file, and matches its bytes to the immutable release asset and deterministic renderer. It checks the source tag and binary digest before fast-forwarding main. If main advances during CI, it rebuilds the metadata branch and requires fresh CI; it never force-pushes main. No release PR is created. The external tap is **optional and off by default** (`PUBLISH_EXTERNAL_TAP=false`) even if `TAP_REPOSITORY` is set. An explicit opt-in requires a writable, non-archived destination and working tap credentials; the archived `maxmeis/homebrew-formulae` repository cannot be used as-is. Neither channel depends on it for in-repo publication. Do not put tokens or signing material in source.

Normal code changes still require PRs and owner review. Release metadata publication uses the verified `maxmeisreleasebot[bot]` GitHub App installation token, minted after the long signing and notarization step. The trusted-main finalizer consumes the verified action output, checks the installation token can access exactly HyperMug, and validates the bot-triggered CI run before updating the cask. Strict CI, force-push/deletion protection, release environment rules, and immutable GitHub Releases remain enforced. Publishing a GitHub Release does not itself prove cask publication or installation; verify downloaded final bytes and the installation/update path before announcing availability. See [Casks](../Casks/README.md) and [Installation](installation.md).

## Automatic Homebrew publication credentials

Configure `RELEASE_BOT_APP_ID`, `RELEASE_BOT_APP_SLUG`, and `RELEASE_BOT_INSTALLATION_ID` as repository variables and `RELEASE_BOT_PRIVATE_KEY` as a repository secret. The shared `maxmeis/release-bot` token action is pinned to a full commit SHA and requests Contents write, Actions read, and Administration read for only `maxmeis/hypermug`. It validates the installation, exact repository and bot identity. The token is consumed within its job; `RELEASE_TOKEN` is not a fallback in App mode. Keep `RELEASE_BOT_ENABLED` unset until exact-main CI and the `Release bot preflight` workflow pass on the merged commit. Then set it to `true` to activate Stable, Canary, and the cask finalizer. Retain the existing `RELEASE_TOKEN` secret until this activation is complete; remove it separately. Git credentials are process-local and never embedded in remote URLs.

The App's publisher exception must be configured only after exact-main CI and runtime preflight pass. Keep required `ci`, branch freshness, non-fast-forward and deletion protection without bypass. The finalizer enforces the single-cask diff and immutable-renderer checks itself. The optional external tap requires its separate SSH deploy key; the App token cannot publish to another repository.

The shared signing wrapper and token action are pinned to release-bot commit `ac8269adb164a9e768bf637169229f9bd0bb4d0e`. Production and beta use the App Store Connect API key notarization mode; the Apple ID fallback requires an explicitly configured separate workflow. The shared signing wrapper sets up the temporary Developer ID keychain and notarization profile inside the protected release job. HyperMug still signs nested Sparkle components and verifies its final ZIP, Sparkle signature, cask and feed. Production and beta environment credentials stay in their current scopes.

## Verified Cask promotion

The trusted Cask finalizer runs on macOS. Before it updates or rebases a Cask candidate, it downloads the immutable ZIP and appcast by their exact release asset IDs, checks their sizes and SHA-256 digests, and safely extracts the ZIP. It rejects traversal, duplicate entries, escaping symlinks, unsupported entry types and oversized archives. It verifies the Developer ID signature and Team ID, hardened runtime, timestamp, stapled ticket, Gatekeeper assessment, arm64 executable, macOS 14 minimum, bundle identity and channel version. The appcast URL, length and versions must match the ZIP, and its Sparkle Ed25519 signature must verify against the reviewed channel public key embedded in the app. Public-key rotation requires a reviewed code change. A failed check leaves main and the published Cask unchanged.

Stable dispatches and reruns are authorized in a secret-free job using the numeric owner and repository IDs and the exact workflow-run-attempt API record. The production job depends on that authorization; Canary remains an automatic protected-main release.
