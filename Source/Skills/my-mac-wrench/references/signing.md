# macOS signing, notarization, and Gatekeeper

Researched 2026-11-16. This is a CLI decision/runbook for release work, not authorization to sign or publish. Check the current [Apple notarization guide](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [distribution signing guide](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac), and [custom notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow) for the chosen Xcode and channel.

## Choose a channel and identity

| Distribution | Identity and path |
| --- | --- |
| Local development | `Apple Development` or the project's configured development signing for debug; a debug/ad hoc build is not a release artifact. |
| Outside the Mac App Store | `Developer ID Application` for app code; `Developer ID Installer` for a signed flat `.pkg` when used. Enable Hardened Runtime, a secure timestamp, and only necessary entitlements, then notarize the deliverable. |
| Mac App Store | Use the App Store distribution identity and Xcode/App Store Connect submission path with the required sandbox/provisioning configuration. Apple says separate Developer ID notarization is not required for App Store distribution. |

Confirm the certificate and **private key** are available in the intended keychain, the identity is valid and chains to Apple, and its Team ID matches the app's distribution configuration. `security find-identity -v -p codesigning` lists code-signing identities; inspect Keychain Access or certificate details for the installer identity. Do not bypass an invalid trust chain or substitute a development/ad hoc identity for a release. Check `CFBundleIdentifier`, helper identifiers, Team ID, bundle versions, and entitlements in the built output, not just project settings. [Apple Developer ID](https://developer.apple.com/developer-id/), [Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/), [Apple signing identities](https://developer.apple.com/documentation/xcode/sharing-your-teams-signing-certificates).

App Sandbox and Hardened Runtime solve different problems. Mac App Store apps generally need App Sandbox; outside-store Developer ID apps need Hardened Runtime for notarization, and may also use App Sandbox when the product requires it. Choose entitlements for each executable's real APIs and channel. Release signatures must not contain `com.apple.security.get-task-allow=true`; that is a development exception. [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Hardened Runtime](https://developer.apple.com/documentation/xcode/configuring-the-hardened-runtime), [security entitlements](https://developer.apple.com/documentation/bundleresources/security-entitlements).

## Build and sign from the inside out

Prefer Xcode's distribution export for Xcode app targets. In a custom CLI build, finish copying every framework, dylib, XPC service, login item, extension, and helper before signing. Sign the deepest nested code first, each with its own appropriate identity and entitlements; frameworks normally should not receive app entitlements or provisioning profiles. Sign the outer app last. If packaging a `.pkg` or DMG, create and sign/notarize containers in the order required by the delivery format. Do not use `codesign --deep` as a signing shortcut: it can apply the wrong entitlements or mask missing per-target decisions. [Apple nested signing](https://developer.apple.com/documentation/xcode/using-the-latest-code-signature-format), [distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac), [packaging](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

For a manually signed Developer ID executable, Apple's documented shape is `codesign -s <Developer-ID-Application-identity> --timestamp -o runtime --entitlements <file> <code>`; omit `--entitlements` where that code has none, and use `-f` only when intentionally replacing a signature. Sign each nested component explicitly. Keep release and debug signing configurations separate. Inspect signatures and entitlements with `codesign -dv --verbose=4 <app>` and `codesign -d --entitlements :- <app>`; verify the full built app with `codesign --verify --deep --strict --verbose=2 <app>` and inspect any failing nested path individually. `--deep` here is for **verification only**. [Apple distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac), [code signing tasks](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html).

## Notarize, staple, and test the final bytes

Use a supported `notarytool` credential method. Locally, `xcrun notarytool store-credentials <profile> --apple-id <id> --team-id <team>` stores an app-specific password in Keychain; CI can use an appropriately protected keychain profile or App Store Connect API key. Do not put credentials or exported `.p12` files in source, command logs, or public artifacts. Use a temporary CI keychain with narrow access, unlock only for the signing job, and remove it after the job. Rotate exposed credentials/certificates through Apple, then re-verify signing, notarization, and update continuity. [Apple notarytool migration](https://developer.apple.com/documentation/technotes/tn3147-migrating-to-the-latest-notarization-tool), [signing identity security](https://developer.apple.com/documentation/xcode/sharing-your-teams-signing-certificates).

1. Archive the signed app with a symlink-preserving tool. For ZIP: `ditto -c -k --sequesterRsrc --keepParent MyApp.app MyApp.zip`. Sparkle warns that flattening framework symlinks breaks signatures. [Sparkle publishing](https://sparkle-project.org/documentation/publishing/).
2. Submit the ZIP, DMG, or signed PKG: `xcrun notarytool submit <artifact> --keychain-profile <profile> --wait`. Require an **Accepted** result; retrieve `xcrun notarytool log <submission-id> --keychain-profile <profile> <log.json>` and inspect errors and warnings. A successful upload alone is not notarization. [Apple custom workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).
3. Staple the app, DMG, or PKG with `xcrun stapler staple <path>` and confirm with `xcrun stapler validate <path>`. A ZIP cannot be stapled; when the submission was a ZIP, staple its contained app and recreate the ZIP, then verify the recreated final archive. Do not replace a published asset after notarization. [Apple custom workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).
4. Download the exact final release asset as a user would, compare its SHA-256 with the recorded checksum, extract it, then run `codesign --verify --deep --strict --verbose=2 <app>` and `spctl --assess --type execute --verbose=4 <app>` (or `--type install` for a PKG). Check the ticket with `stapler validate` and launch/install on a clean or representative Mac. Check quarantine on the normal download and the extracted app as applicable (`xattr -p com.apple.quarantine <path>`); a test without the quarantine state on the launched app does not exercise the same Gatekeeper path. Never disable Gatekeeper or strip quarantine to make the test pass. [Apple code-signing assessment](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html), [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

If a step fails, use the notary JSON issue `path` and message, `codesign` verification, bundle identifiers, certificate chain/private key, timestamp, hardened-runtime flags, entitlements, nested-code order, and ZIP symlinks to find the specific fault. A ticket cannot repair an invalid signature. Rebuild and reverify a new artifact before publication; preserve released tag and asset immutability. Apple's notary service no longer accepts `altool` uploads, so use `notarytool`, not legacy commands. [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).
