# Native macOS interface decisions

Researched 2026-11-16 against Apple's current [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos), [menus](https://developer.apple.com/design/human-interface-guidelines/menus), [settings](https://developer.apple.com/design/human-interface-guidelines/settings), and [accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) guidance. Use this for app UI work, not for an unrelated code-only change.

## Select the UI technology for the interaction

Choose SwiftUI for scene-based views, ordinary settings and forms, and a simple `MenuBarExtra` when its lifecycle and menu presentation fit. Choose AppKit for precise status-item/menu control, advanced window/panel focus and placement, or interaction APIs that SwiftUI does not expose cleanly. Mix them deliberately with `NSHostingView`/`NSHostingController` or representable wrappers rather than rewriting working native behavior to satisfy a framework preference. Establish the service/state contract before building the interface so the UI can reflect real permission, device, and error states. [SwiftUI `MenuBarExtra`](https://developer.apple.com/documentation/swiftui/menubarextra), [AppKit integration](https://developer.apple.com/documentation/swiftui/appkit-integration), [AppKit `NSStatusItem`](https://developer.apple.com/documentation/appkit/nsstatusitem).

## Mac interaction patterns

- For a menu-bar utility, expose frequent, glanceable actions in the extra. Use standard menu items for commands, checked states for persistent toggles, disabled states for temporarily unavailable actions, and an ellipsis when a command needs more input. Give users an understandable path to Settings, Help, and Quit; avoid a status icon as the only path to critical control. Menu-bar space is limited and status items are not guaranteed to be visible. [Apple menus](https://developer.apple.com/design/human-interface-guidelines/menus), [`NSStatusBar`](https://developer.apple.com/documentation/appkit/nsstatusbar).
- Use a window for sustained work and a panel for supplementary controls that relate to another window or selection. Check activation, key-window ownership, focus restoration, click-away dismissal, and window placement when the app uses popovers or floating panels. Put app settings in the standard Settings command/window and support Command-Comma; document-level options belong with the document. [Apple panels](https://developer.apple.com/design/human-interface-guidelines/panels), [settings](https://developer.apple.com/design/human-interface-guidelines/settings).
- Make ordinary app commands available through the macOS menu bar and keyboard. Preserve established shortcuts, including editing/undo conventions; avoid stealing system shortcuts or relying on a pointer-only control. Test menu commands while another window is active and after the app is reactivated. [Apple keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards), [undo and redo](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo).
- Test window movement/resizing across displays, display disconnect, Spaces/full-screen transitions, app activation/deactivation, and relaunch only when the feature touches those states. Keep a popover or panel reachable when the active display or Space changes. [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos), [AppKit windows and screens](https://developer.apple.com/documentation/appkit/windows-panels-and-screens).
- For manually placed normal windows, use the current screen's `visibleFrame` rather than assuming the full `frame` is unobstructed; re-evaluate placement when the Dock, menu bar, or display layout changes. Use the full `frame` only for interfaces intentionally spanning those areas. [Apple `NSScreen.visibleFrame`](https://developer.apple.com/documentation/appkit/nsscreen/visibleframe).

## Appearance and accessibility

Use system controls, materials, colors, and SF symbols where they fit. Check light, dark, and automatic appearance while the app is running; avoid hardcoded contrast assumptions. Provide a readable status icon in both appearances. Prefer system fonts and readable text sizing; let custom text wrap or resize without clipping. **macOS does not support user-adjustable Dynamic Type**: SwiftUI's `dynamicTypeSize` does not change Mac text size from a user setting. Offer app-level text scaling where the product needs it instead of claiming iOS Dynamic Type support. [Apple Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode), [typography](https://developer.apple.com/design/human-interface-guidelines/typography), [SwiftUI dynamic type on macOS](https://developer.apple.com/documentation/swiftui/environmentvalues/dynamictypesize).

Treat the app icon and menu-bar/status image as different surfaces. Follow the app-icon guidance for recognizable branding and current appearance variants; use a simple template `NSImage` or suitable SF Symbol for monochrome status controls that adapt to their surrounding appearance. Inspect the actual rendered icon at menu-bar size and in both appearances; `isTemplate` expects black and transparent content rather than a full-color logo. [Apple app icons](https://developer.apple.com/design/human-interface-guidelines/app-icons), [`NSImage.isTemplate`](https://developer.apple.com/documentation/appkit/nsimage/istemplate).

Make every primary control keyboard reachable with a visible focus path and a meaningful VoiceOver label, value, and state. Native controls provide much of this; custom controls and status items need explicit inspection. Check Full Keyboard Access, VoiceOver reading/order, high contrast, differentiation without color, and reduced motion for the actual interface. AppKit exposes `NSWorkspace.accessibilityDisplayShouldReduceMotion` and a display-options change notification; avoid gratuitous animation when it is enabled. [Apple VoiceOver](https://developer.apple.com/design/human-interface-guidelines/voiceover), [accessibility testing](https://developer.apple.com/documentation/accessibility/testing-system-accessibility-features-in-your-app), [reduce motion API](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldreducemotion).

For a new interface, sketch only enough to decide hierarchy and interaction. Validate it in a running native app at realistic window sizes and system settings; a mockup does not establish menu focus, permission UX, or accessibility behavior.
