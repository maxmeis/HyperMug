# Versioned macOS releases

Researched 2026-11-16. Recheck current GitHub, Apple, and updater documentation for the project's actual release path. This reference guides release work only; it does not authorize publication.

## Choose the release mode before creating the tag

Every published version gets one stable, immutable version tag and a GitHub Release pointing to the approved source commit. Keep the tag, release title/notes, source commit, and any built app's `CFBundleShortVersionString` (marketing version) and increasing `CFBundleVersion` (build version) consistent. Record source SHA, build provenance, supported macOS/architectures, distribution mode, and verification results in the release notes. Apple distinguishes the user-visible marketing version from the build identifier; Sparkle compares the build version. [Apple bundle versions](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution), [Sparkle versioning](https://sparkle-project.org/documentation/).

Use an explicit release policy or build Boolean such as `build_app=true|false`; do not infer it from whether a signing key happens to be available. Two valid modes:

| Mode | Publish | Do not publish or claim |
| --- | --- | --- |
| **Compiled artifact** | Build and test the approved commit on macOS; sign and notarize for the chosen outside-store channel; package, verify, then attach immutable `.zip`, `.dmg`, or `.pkg` assets with actual checksums and install instructions. Update Sparkle or a cask only after the final bytes are public and tested. | A binary release based only on an unsigned CI build or a draft asset. |
| **Source-only** | Tag the approved commit and publish a GitHub Release that clearly says “source-only”, with changes, prerequisites, and local build instructions. GitHub's automatic source archives remain source archives. | A compiled app, installer link, checksum, cask revision, Sparkle entry, signing or notarization claim, or promise that users can install a binary. |

For a compiled release on a remote macOS runner, pin the runner to the approved SHA/tag, run build and tests, export/sign and notarize for Developer ID delivery, package and verify the exact final asset, then publish the draft with release notes and provenance. Keep signing details in [signing.md](signing.md). For a source-only release, publish without binary assets. A release can be source-only by design; lack of a binary is not a failed release. Keep `latest` pages and README download buttons honest: GitHub's `releases/latest` may point at the latest published full release even if it is source-only, while `/releases/latest/download/<asset>` assumes that named asset exists. Prefer a version-specific binary URL or an explicit “latest binary” pointer managed separately when source-only versions are possible. Check prerelease/latest settings and version ordering before publishing. [GitHub release management](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository), [release links](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases), [latest release API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release).

Do not move a published tag or replace a published artifact to turn a source-only version into a compiled one. GitHub's immutable-release setting makes this technically impossible after publication; even without it, stable tags and assets are a supply-chain promise. If same-version binary publication is required, keep the release as a draft until the binary is ready. If source-only was already published, make the later binary a new version with a new commit/tag and consistent bundle version; cite the earlier source-only release in the notes. Keep update feeds and cask versions monotonic. [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases).

## Keep configured channels separate

If the project offers Stable and Canary, preserve both as deliberate release policies. For example, Canary may build automatically from approved changes on the app's main branch while Stable requires a manually selected version and commit. Give each published channel build a unique immutable tag, release, and artifact identity; mark Canary GitHub Releases as prereleases where that matches the product's download policy. Do not let an automated Canary run advance Stable's download link, cask, or update feed. Publish a source-only release in either channel only with the source-only claims above; it advances no binary pointer in that channel. Check GitHub's latest-release behavior and any custom download buttons against the actual release flags and assets. [GitHub releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository), [release links](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases).

Store a user's selected update channel and show it in Settings. With Sparkle 2, `allowedChannelsForUpdater` adds named channels **alongside** the default channel; it cannot exclude default-channel updates. That is useful when Canary users should also receive Stable builds, but it does not strictly isolate a user who must receive only Canary. For strict selection, use separate channel-specific feeds through `feedURLStringForUpdater` (or another supported selection design), keep a default `SUFeedURL`, and test changing channels and update checks. Avoid deprecated `setFeedURL:`. Plan `CFBundleVersion` ordering across feeds and channel switches so Sparkle never needs to downgrade; a manually promoted Stable build may need a higher build number than the newest Canary build users can have. Test Stable→Canary and Canary→Stable from real installed builds, including no eligible update and a skipped version. [Sparkle channels and feeds](https://sparkle-project.org/documentation/publishing/), [Sparkle updater delegate](https://sparkle-project.org/documentation/api-reference/Protocols/SPUUpdaterDelegate.html), [Sparkle programmatic setup](https://sparkle-project.org/documentation/programmatic-setup/).

## Artifact and update checks

- Verify the final uploaded bytes, not an intermediate archive: `shasum -a 256 <asset>`; compare with the downloaded release asset. Inspect `Info.plist`, architectures, code signatures, notarization ticket, and installation on a clean or representative Mac. Keep the source SHA and release asset digest recorded. GitHub release assets expose a digest in the [REST release response](https://docs.github.com/en/rest/releases/releases).
- For outside-store apps using Sparkle, preserve framework symlinks and executable permissions in archives. Use Sparkle's `generate_appcast` or signing tools on the **final** archive. Check enclosure URL, EdDSA signature, size, release notes, `sparkle:version` against `CFBundleVersion`, and `sparkle:shortVersionString` against the marketing version; perform an actual update from an older installed build. Do not advance a feed for source-only versions. [Sparkle publishing](https://sparkle-project.org/documentation/publishing/), [Sparkle sandboxing](https://sparkle-project.org/documentation/sandboxing/).
- If GitHub Actions builds the release, pin the build to the intended tag/SHA, use protected secrets and narrow token permissions, and keep an untrusted PR's code out of privileged jobs. A compiled asset and its cask/update metadata should be traceable to one approved source version. [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use).

Finish with user-facing release notes and an installation-first README for the actual mode. Never describe a source-only release as a downloadable Mac app.
