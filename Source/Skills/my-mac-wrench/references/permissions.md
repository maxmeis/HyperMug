# macOS permissions and system integration

Researched 2026-11-16. Recheck the exact API and minimum macOS version before adding a permission claim. TCC grants are decisions made by the user/system; this reference never authorizes editing the TCC database, resetting global grants, or prompting repeatedly.

## Map the feature to its real permission

| Capability | Check/request path | Important distinction |
| --- | --- | --- |
| Control another app's UI with Accessibility APIs | `AXIsProcessTrustedWithOptions`, with `kAXTrustedCheckOptionPrompt` only when an explanation and request are appropriate. | Accessibility is not a blanket grant for listening to input or recording the screen. The prompt is asynchronous. [Apple Accessibility API](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions). |
| Listen to low-level keyboard/input events | `CGPreflightListenEventAccess` / `CGRequestListenEventAccess` for Input Monitoring where the chosen event API requires it. | Choose passive versus filtering taps deliberately; do not request Accessibility and Input Monitoring by habit. Test the actual event type and macOS release. [Core Graphics access APIs](https://developer.apple.com/documentation/coregraphics/core-graphics-functions), [event taps](https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate%28tap%3Aplace%3Aoptions%3Aeventsofinterest%3Acallback%3Auserinfo%3A%29). |
| Capture a display, window, or app | `CGPreflightScreenCaptureAccess` / `CGRequestScreenCaptureAccess`, or the appropriate ScreenCaptureKit picker and capture path. | Window-list side effects are not a reliable permission test. ScreenCaptureKit's system picker can narrow what is shared. [Core Graphics screen preflight](https://developer.apple.com/documentation/coregraphics/cgpreflightscreencaptureaccess%28%29), [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit). |
| Send Apple events to another app | Explain `NSAppleEventsUsageDescription`; for sandboxed apps, assess the Apple Events entitlement and target-specific behavior. | Automation targets and the relevant sandbox entitlements differ from Accessibility UI control. [Apple protected resources](https://developer.apple.com/documentation/bundleresources/protected-resources), [security entitlements](https://developer.apple.com/documentation/bundleresources/security-entitlements). |
| Use camera, microphone, audio capture, files, location, Bluetooth, etc. | Use that framework's authorization status/request API, purpose string, and entitlement where required. | Each resource has its own policy. For camera/mic, request only at feature use; missing usage strings can terminate the app. [Apple media authorization](https://developer.apple.com/documentation/bundleresources/requesting-authorization-for-media-capture-on-macos), [protected resources](https://developer.apple.com/documentation/bundleresources/protected-resources). |

Preflight without prompting when possible. Explain the concrete feature and data use immediately before a request. If access is denied, restricted, revoked, or still pending, show accurate status and offer the supported System Settings path or a degraded mode; do not loop prompts at launch. Recheck status when returning from Settings and before starting protected work. Some APIs/OS versions may require relaunch after a grant: demonstrate that for the **exact** feature and documented behavior, rather than making restart universal. Apple's ScreenCaptureKit sample requires restart after the first Screen Recording grant, which does not prove the same for all TCC services. [Apple media authorization](https://developer.apple.com/documentation/bundleresources/requesting-authorization-for-media-capture-on-macos), [ScreenCaptureKit sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos).

Treat the app's installed identity as part of permission testing. A debug/ad hoc build, Developer ID build, Mac App Store build, moved bundle, or differently signed helper may be seen differently. Keep bundle identifiers, Team ID, signing requirements, and launch location stable for the path users will run. When a grant appears lost, inspect the actual signed app/helper and responsible process before suggesting a user regrant. Apple DTS notes that ad hoc signatures give unstable identity and cause TCC problems. Do not edit TCC storage or reset every app's grants to repair a release. A narrowly scoped `tccutil reset <service> <bundle-id>` can be useful in an **authorized local test**, but it is not an app setup step. [Apple DTS signing advice](https://developer.apple.com/forums/thread/751658), [Apple TCC reset scope](https://developer.apple.com/documentation/xcode/resetting-access-to-protected-resources-in-macos).

## Input, devices, and lifecycle

- Event-tap callbacks run on their attached run loop. Keep them short and nonblocking, avoid UI work/reentrant input posting inside the callback, and return the original event when filtering cannot safely decide. Handle tap creation failure and `.tapDisabledByTimeout`/`.tapDisabledByUserInput`; re-enable only when permission and user intent still allow it. Remove run-loop sources and release the Mach port during teardown. This **fail-open input** behavior prevents a utility fault from swallowing user input. [Apple event-tap creation](https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate%28tap%3Aplace%3Aoptions%3Aeventsofinterest%3Acallback%3Auserinfo%3A%29), [tap-disabled event types](https://developer.apple.com/documentation/coregraphics/cgeventtype).
- Respect Secure Event Input. It can prevent observation of sensitive input; do not work around it, infer which app enabled it, or log captured keystrokes. Apple DTS identifies `IsSecureEventInputEnabled` as a way to inspect the global state but says the responsible app cannot be reliably identified. [Apple DTS on secure input](https://developer.apple.com/forums/thread/848711).
- For hardware-backed features, model attach/detach, sleep/wake, unsupported devices, and lost permissions as state transitions. Close handles and remove observers on detach/exit; re-enumerate and reconcile once after wake instead of assuming old handles remain valid. Keep callbacks thread-safe and hand UI changes to the appropriate main-thread/actor context. `NSWorkspace` offers sleep/wake notifications through its own notification center. [Apple `NSWorkspace` lifecycle](https://developer.apple.com/documentation/appkit/nsworkspace), [wake notification](https://developer.apple.com/documentation/appkit/nsworkspace/didwakenotification).
- For supported login items/helpers on macOS 13+, prefer `SMAppService` with the helper inside the app bundle, inspect `status`, and test user disable/re-enable and upgrades. Explain why the helper runs; do not silently reinstall a user-disabled service. Check older-OS support separately. [Apple `SMAppService`](https://developer.apple.com/documentation/servicemanagement/smappservice), [updating helpers](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos).

Collect only the input and system data needed for the feature. Redact key events, window titles, device identifiers, and permission details in routine logs; avoid logging secrets or full captured content. Make diagnostics opt-in or bounded when they could include sensitive state. Test onboarding, denial, revocation, app restart, sleep/wake, and hardware loss with the **release-signing identity** when those paths are in scope.
